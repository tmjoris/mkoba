# Reading M-Pesa messages with a small language model: what helped

Mkoba's treasurer can paste the M-Pesa messages members' payments produced, and the app
turns each one into a proposed contribution. This folder is how I measured whether a
language model makes that better, and how I changed the design because of what I found.

## The question

A chama treasurer gets a payment SMS for most contributions and types each one into the
books by hand. Most of those SMS follow one format that a regular expression reads exactly.
The rest do not: Swahili SMS, messages that wrap or lose spaces when copied, a payment
forwarded with "hii ni ya Mary", or a member's own note ("nimetuma 2k"). Can a model the
size of Apple's on-device model read those, and what does it cost when it is wrong?

What wrong costs is the point. A model that records a payment against the wrong member, or
records money the treasurer *sent* as money received, puts a mistake in the group's books
with one tap. So every system is scored from the treasurer's side:

| Outcome | Meaning |
|---|---|
| **Correct** | Did what a careful treasurer would: recorded with the right member, amount, code and cycle; sent to a person when a person must decide; skipped what is not a payment. |
| **Wrong** | One tap would put something wrong in the books. The number that matters most. |
| **Flagged** | Sent to the treasurer to check when it could have been recorded or skipped. Safe, costs time. |
| **Missed** | A payment (or something to check) dropped as "not a payment". |

## How it works

The model never decides anything about money. It fills in a `@Generable` struct with text
**copied** from the message (the code, the amount as written, the sender, the date), using
guided generation so its output always has that shape. Plain Swift then turns the text into
an amount, a member and a contribution cycle, and checks it against the message and the
books (`Sources/MkobaCore/Import`):

- the code, amount, name and phone must actually be in the message;
- the amount must not be the M-Pesa balance (English "balance", Swahili "salio");
- only M-Pesa's own confirmation ("Confirmed" / "Imethibitishwa") is proof, and only if it
  says the money was *received*; a member's note is a claim to check;
- the code must not already be in the books or appear twice in the paste;
- exactly one member must match, by phone first and name second (the eval chama has two
  Wanjikus and two Otienos on purpose).

The same `ModelReader` runs against Apple's on-device model on iOS 26 (through
[AnyLanguageModel](https://github.com/huggingface/AnyLanguageModel), which mirrors the
Foundation Models API) and against open models in Ollama on Linux, which is how it is
evaluated here.

## The test set

[`messages.jsonl`](messages.jsonl): 52 labelled messages, generated by
[`make_messages.py`](make_messages.py). **All are synthetic**: written to look like the SMS
a treasurer receives, for the ten made-up members of `EvalChama`. They are not real
messages, and the formats are my approximation of M-Pesa's.

| Kind | Count | Should be |
|---|---|---|
| Standard SMS (full or masked phone, amount equal to balance, October and midnight dates) | 19 | recorded |
| Paid by someone else, forwarded with a note naming the member | 3 | recorded |
| Swahili SMS | 3 | recorded |
| Copied badly: wrapped lines, lower case, WhatsApp header, spaces lost | 4 | recorded |
| Surname only, or a sender who is not a member, or a bank | 4 | checked |
| A member's own note ("nimetuma 2k", "sent 1500") | 5 | checked |
| Code already in the books | 1 | checked |
| Money sent, paid, withdrawn, airtime, Fuliza, M-Shwari, reversal, balance, chat | 13 | skipped |

## Runs

Every model run happens on GitHub Actions (`.github/workflows/assist.yml`): Ollama as a
service container, each model's 52 messages split across four standard runners (4 CPUs,
no GPU), greedy decoding. Raw readings for every message are in `runs/N/`.

### Run 1: first version of the checks

Out of 52 messages, with the checks on (with them off in brackets):

| Reader | Correct | Wrong | Flagged | Missed | Seconds per message |
|---|---|---|---|---|---|
| Regular expression only | 41 | **0** (3) | 1 | 10 | 0 |
| qwen2.5 3B | 19 | **1** (11) | 32 | 0 | 16.6 |
| llama3.2 3B | 38 | **3** (12) | 11 | 0 | 19.3 |
| gemma3 4B | 42 | **2** (8) | 6 | 2 | 24.6 |
| qwen2.5 7B | 38 | **3** (11) | 11 | 0 | 34.0 |

What I found reading the [raw readings](runs/1):

- **Trusted, every model would have put 8 to 12 wrong entries in the books.** The checks
  stopped most of them.
- **Nearly every remaining wrong entry was money going out**: Ksh 2,000 the treasurer sent
  to Mary, a withdrawal at an agent called KAMAU AGENCIES, airtime bought for Peter's
  number. The models marked them as money received, and those messages are confirmed by
  M-Pesa in the same format, so my checks passed them.
- qwen2.5 3B wrote every phone number with a leading `*` ("*0712345678"), because my field
  description mentioned `*` for masked numbers. That flagged 20 readings that were otherwise
  correct.
  One model wrote a date with JSON-escaped slashes ("3\/11\/26").
- The 7B model was no better than the 3B ones, at twice the time.
- The regular expression never records anything wrong, but it silently drops every Swahili
  and every badly copied SMS.

### Run 2: check that the money was received

Changes: a new check that M-Pesa's message says the money was *received* ("received",
"umepokea"); a stray `*` around a phone number and escaped slashes in a date are ignored;
clearer field descriptions; one retry if a model call times out.

| Reader | Correct | Wrong | Flagged | Missed | Seconds per message |
|---|---|---|---|---|---|
| Regular expression only | 41 | **0** (3) | 1 | 10 | 0 |
| qwen2.5 3B | 39 | **0** (10) | 13 | 0 | 13.4 |
| llama3.2 3B | 38 | **0** (11) | 14 | 0 | 14.5 |
| gemma3 4B | 42 | **0** (8) | 8 | 2 | 25.3 |
| qwen2.5 7B | 39 | **0** (11) | 13 | 0 | 38.1 |

No model recorded anything wrong. The clearer descriptions barely changed what the models
did on their own (still 8 to 11 wrong when trusted): **the safety comes from the checks,
not the prompt.**

But most of what was left as "flagged" was money going out that the checks now caught,
put in front of the treasurer as "Check". That is safe and a waste of the treasurer's time:
M-Pesa's own words already say it is not a payment.

### Run 2 re-scored: money going out is skipped, not flagged

Change: a confirmation that does not say the money was received is "Not a payment", with
the reason shown. Measured by re-scoring run 2's saved readings, so the models' readings
are identical and only the checks differ.

| Reader | Correct | Wrong | Flagged | Missed | Seconds per message |
|---|---|---|---|---|---|
| Regular expression only | 41 | **0** | 1 | 10 | 0 |
| qwen2.5 3B | **49** | **0** | 3 | 0 | 13.4 |
| llama3.2 3B | 47 | **0** | 5 | 0 | 14.5 |
| gemma3 4B | **49** | **0** | 1 | 2 | 25.3 |
| qwen2.5 7B | **49** | **0** | 3 | 0 | 38.1 |
| Rules first, then qwen2.5 3B | **49** | **0** | 3 | 0 | 5.6 |

What the model adds over the regular expression: the 3 Swahili and 2 badly copied payments
are recorded instead of dropped, and the 5 members' notes reach the treasurer as "Check"
instead of disappearing (gemma3 drops two of them). For qwen2.5 3B, what is still flagged is a forwarded "Hii ni ya Mary Achieng" where
the model did not fill in who the money was for (safe: no member matched), a chat message
quoting "Ksh2,000", and one model call that failed twice.

### Run 3: the same again

Run 3 repeated run 2's models and prompt with the final checks, to see how much a rerun
moves. Wrong stayed at **0** for every model; correct moved by at most one (gemma3 4B 48,
llama3.2 3B 47, qwen2.5 3B 49, qwen2.5 7B 48). Greedy decoding was not perfectly repeatable
on these runners: between runs 2 and 3, 1 or 2 of the 52 readings changed for qwen2.5 and
llama3.2, and 11 for gemma3. The checks are what keep the outcome stable when the readings
are not. [Raw readings](runs/3).

### Design decision: rules first

Reading every message with the model, or only the ones the regular expression cannot read,
gives the same accuracy in run 2 and its re-score: on the standard SMS both are right. Rules first
asks the model about 23 of the 52 messages, cutting model time per message by about 60%,
and standard SMS appear instantly. That is how the app works: `MessageImporter` uses the
regular expression, then Apple's on-device model for the rest when Apple Intelligence is on,
and the same checks for everything.

## What this does not show

- **Apple's on-device model was not tested.** It needs an Apple silicon device with Apple
  Intelligence, and I develop on Linux. The open 3–4B models stand in for it because it is
  about the same size; the code path is the same, but its accuracy may differ.
- **52 synthetic messages are a small test set.** Real treasurers' messages would find
  formats I did not think of. Each table is one run; run 3 shows how much a rerun moves.
- **Time per message is on a CPU-only runner**, not on a phone's Neural Engine.
